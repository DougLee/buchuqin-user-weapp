# 日夜查询故障隔离（2026-11-17）

本轮仅调整用户端与配送端的 `feature/night-store` worktree，没有修改 API、数据库结构或生产环境。

## 决定与实现

- 配送端白天待办与夜宵查询各自执行、各自防止重叠请求。夜宵状态或订单查询失败、超时、持续等待，都不会阻止白天下一轮检查；白天请求失败也不阻止夜宵更新。
- 保留 30 秒轮询周期、首拍建立基线及增量提醒规则。切号、前后台切换后，旧响应与旧请求的清理逻辑不能影响新请求。
- 用户端先读取现有 `/campus/current` 的有效 `nightEnabled`。只有服务端明确返回 false，才直接确定白天渠道，跳过夜宵入口及其附带地址查询。
- 已开通校区仍通过夜宵入口确认本楼经营状态；失败进入重试，不加载另一渠道。旧 API 缺少开通字段、校区请求失败、身份或地址已改变，均不能据此猜测白天。
- 复用现有渠道 store 的 60 秒缓存、并发去重、身份失效和首页重试界面。首页每次主动刷新重新核验校区开关；夜宵结算仍独立核验实际营业资格。

## 验证

代码修改完成后集中运行测试：

- 用户端共 82 条脚本用例：全量运行 79 条通过，3 条登录恢复测试补充新增校区请求夹具后定向复测通过。新增测试覆盖未开通首页、开通后等待、失败重试、开关变化、换号及换地址晚到响应。
- 配送端全量 38 条脚本用例通过，包含接口失败、请求等待/超时、双向隔离、通知去重、切号及前后台切换。
- 两端 TypeScript、H5 构建及微信小程序构建均通过；构建显式使用测试 API 地址，没有发布小程序。

本地 H5 使用固定转发至 `127.0.0.1:3160` 的故障代理，仅对本轮隔离账号注入失败；没有连接生产。结果：

1. 校区未开通且夜宵入口配置为失败：白天首页正常加载，夜宵入口请求为 0。
2. 校区开通且夜宵入口返回 500：首页显示重试，不请求白天商品。恢复接口并重试后，正确显示夜宵商品。
3. 夜宵订单响应延迟 45 秒，保留真实 30 秒轮询周期：33 秒观察内，白天待办分别在第 8 毫秒、第 30009 毫秒请求；夜宵只发出 1 次请求。
4. 夜宵状态、夜宵订单分别返回 500：同轮白天待办均正常发出。

本地验收校区完成后恢复关闭，注入模式恢复正常。没有调用微信支付、退款或真实推送；这些原生能力仍按原验收清单单独验证。
